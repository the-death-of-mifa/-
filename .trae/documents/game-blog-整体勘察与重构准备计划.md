# 游戏博客项目整体勘察与重构准备计划

## Summary

- 目标：对当前游戏博客项目做一次基于真实代码的整体化遍历与结构认知，形成一份可直接指导后续重构执行的准备计划。
- 本次会话范围：仅聚焦前端现状分析、前端重构准备、重构阶段顺序建议，不实施代码修改。
- 已确认方向：后续重构优先级为“结构模块化”；技术边界接受“框架化迁移”；未来会接入一个可服务多个前端的主站后端，但当前会话先做前端优化准备。
- 核心结论：应先完成前端结构清理与模块边界重建，再规划后端接入；视觉精修应放在结构稳定之后。

## Current State Analysis

### 1. 仓库形态

- 项目不是工程化前端工程，仓库根目录直接以静态文件组织。
- 页面入口真实存在以下文件：
  - `index.html`：当前主首页。
  - `index2.html`：与首页高度重复，疑似历史副本或备用页面。
  - `contact.html`：联系页。
  - `live.html`：旅行/相册页。
  - `showmd.html`：独立的 Markdown 展示页。
- 主要资源目录：
  - `css/`：公共样式和页面专属样式。
  - `js/`：公共交互、首页交互、Canvas 背景及第三方库。
  - `img/`：图片、音频和背景资源。

### 2. 页面与资源依赖关系

- `index.html`、`contact.html`、`live.html`、`index2.html` 共享同一套基础资源：
  - `css/base.css`
  - `js/jq.js`
  - `js/base.js`
  - `js/paper-full.min.js`
  - `js/canvas.js`
- 页面级差异资源：
  - `index.html` / `index2.html` 额外加载 `css/index1.css` 与 `js/index1.js`
  - `contact.html` 额外加载 `css/contact.css`
  - `live.html` 额外加载 `css/live.css`
- `showmd.html` 完全独立，使用：
  - `css/prism.css`
  - `css/prism-line-numbers.css`
  - `css/font-awesome.min.css`
  - `js/marked.js`
  - `js/prism.js`
  - `js/jquery.min.js`

### 3. 当前前端架构特征

- 架构本质为“多 HTML 页面 + 公共 CSS/JS 直接复用 + 页面局部差异内容”的手工拼接模式。
- 公共布局在多个页面中直接复制，未抽象为模板、组件或局部片段。
- 公共脚本使用 jQuery 直接面向具体 DOM 选择器绑定事件，没有模块初始化边界。
- 主题切换通过 `sessionStorage` 保存布尔状态，运行时直接修改 CSS 变量。
- Canvas 星空背景通过 `paper-full.min.js + canvas.js` 在多个页面复用。

### 4. 现有职责拆分

#### `js/base.js`

- 职责：
  - 初始化主题状态。
  - 绑定主题切换。
  - 绑定页面滚动时左侧卡片吸附。
  - 绑定移动菜单显示/隐藏。
  - 处理加载层淡出。
  - 处理锚点平滑滚动。
  - 处理视频遮罩关闭。
- 问题：
  - 对 `#mycard`、`#myRadio`、`#zhezhao`、`#minmenu` 等节点存在强假设。
  - 逻辑面向“整站页面都具备同构 DOM”，可维护性弱。
  - 存在调试输出。
  - 未做按页面能力拆分。

#### `js/index1.js`

- 职责：
  - 首页轮播/平移逻辑。
  - 视频播放弹层开启。
  - 音乐播放切换。
- 问题：
  - 当前 HTML 中缺少其依赖的多个节点：
    - `#leftimg`
    - `#rightimg`
    - `#li5boxul`
    - `#playbuttom`
  - 说明该脚本包含残留功能或半删除状态逻辑。
  - 现阶段不适合作为未来重构的可信基础，应先清点和裁剪。

#### `js/canvas.js`

- 职责：
  - 初始化 `paper.js` 画布。
  - 构建星空背景。
  - 处理鼠标移动与视图刷新。
- 特征：
  - 独立性相对较高。
  - 可以作为未来组件化时保留的“视觉背景模块”候选。

#### `contact.html` 内联脚本

- 当前通过 `sendEmailEvent()` 弹出“发送成功”并清空表单。
- 不包含真实提交逻辑，也未接入后端接口。
- 说明当前联系页只是静态演示，不具备真实业务能力。

#### `showmd.html`

- 职责：
  - 读取 URL 参数 `mdfile`
  - 发起 Ajax 请求加载 Markdown
  - 使用 `marked` 转 HTML
  - 使用 `Prism` 高亮代码
  - 双击代码块复制文本
- 特征：
  - 与主站视觉/逻辑体系基本独立。
  - 路径策略与主站不统一，采用 `/css`、`/js` 绝对路径。

### 5. 样式现状

#### `css/base.css`

- 承担内容：
  - 全局 CSS 变量
  - 顶部栏、导航区、左侧卡片、按钮、加载层、遮罩层、菜单、响应式布局
  - 音乐播放器样式
  - Canvas 层级控制
- 问题：
  - 文件体量较大，公共基础样式与具体业务块样式混杂。
  - 平板/手机规则分散但整体仍围绕当前耦合布局编写。

#### `css/index1.css`

- 承担首页专属模块样式，但内部包含多块当前页面已未使用或不完整使用的样式：
  - 视频区块 `.li3-box`
  - 轮播区块 `.li5-box`
  - 其他多段卡片区块
- 发现问题：
  - 存在缺失资源引用：`../img/videoback.jpg`
  - 与当前 DOM 不完全匹配，可信度下降

#### `css/contact.css`

- 主要是联系页输入区样式。
- 规模较小，可较容易迁移为独立页面模块样式。

#### `css/live.css`

- 包含旅行图片卡片布局与顶部统计卡样式。
- 与 `css/index1.css` 在 `.content-li.li1`、`.li1-box` 等块上存在明显重复定义。

### 6. 已确认的结构性问题

- 页面模板重复严重：
  - 页头
  - 导航 Hero
  - 左侧个人卡片
  - 菜单/主题切换
  - 加载层
  - Canvas 背景
- 公共脚本与页面 DOM 结构深耦合，页面一旦改结构，公共 JS 很容易失效。
- 存在残留代码、未引用文件、缺失资源：
  - `js/resume.js` 无实际作用
  - `css/index1.css` 引用了不存在的 `img/videoback.jpg`
  - `index1.js` 中多个绑定节点当前页面不存在
- 交互方式偏旧：
  - 大量 jQuery 直接绑定
  - `onclick`
  - `javascript:history.back()`
  - `document.execCommand("copy")`
- 内容与结构未分离：
  - 文案、链接、媒体地址直接写死在 HTML 中
  - 外部视频地址直接内嵌在首页
- 与未来后端接入不兼容：
  - 当前没有数据模型边界
  - 没有表单提交流程
  - 没有用户状态管理
  - 没有 API 层

## Assumptions & Decisions

### 已确认决策

- 当前会话不做后端实现，只做前端优化准备。
- 后续重构主目标优先是“结构模块化”，不是先做纯视觉翻新。
- 技术边界允许框架化迁移，因此本次准备不应局限于“继续修补 jQuery 静态页”。

### 顺序决策

- 推荐执行顺序：
  1. 先做前端结构重构准备与信息抽取。
  2. 再做前端模块化/组件化改造。
  3. 在前端信息架构稳定后，再对接后端接口层。
  4. 最后做视觉精修和交互细节打磨。
- 不建议先做后端：
  - 当前前端页面结构重复且数据边界未定义。
  - 如果先做后端，接口设计会被当前不稳定页面结构绑住，后续前端重构时还要返工接口契约。
- 不建议先做视觉化：
  - 当前最大成本不是“长得不够新”，而是“结构难改、重复过多、逻辑边界模糊”。
  - 在旧结构上先做视觉润色，会放大后续重构返工量。

### 对未来后端的前端前置要求

- 虽然本次不做后端，但前端重构准备中必须提前保留以下接口位：
  - 用户认证入口：注册、登录、退出、鉴权状态
  - 内容数据入口：文章、项目、相册、联系信息
  - 文件/媒体资源入口：封面图、背景图、视频、音频
  - 公共 API 层与错误处理层
- 因此本次计划应以“将静态内容拆成可配置内容结构”为前置目标。

### 1. 本次规格目标

- 产出一份足以支撑后续执行阶段的细分重构规格。
- 规格必须建立在“业务源码已读全、依赖关系已知、遗留文件已识别”的前提上。
- 规格要解决的不是“立刻写代码”，而是“后续改造不再靠猜”。

### 2. 本次规格不做的事

- 不直接修改前端代码。
- 不直接接后端接口。
- 不先做视觉美化稿。
- 不手动改写任何第三方库源码。

### 3. 执行阶段必须遵守的前置检查

- 改任一页面前，先确认该页面完整依赖链。
- 改任一公共文件前，先确认受影响页面清单。
- 删除任一文件前，先确认：
  - 仓库内无直接引用
  - 页面内无隐性结构依赖
  - 后续迁移方案中无保留用途
- 抽公共组件前，先确认各页面真实差异点，避免过度抽象。

### 4. 细分任务树

- T0：建立页面与资源依赖地图
- T1：建立一方源码阅读覆盖表
- T2：建立公共布局候选清单
- T3：建立公共脚本与页面脚本分界表
- T4：建立重复样式归并表
- T5：建立死代码与缺失资源清单
- T6：建立内容模型与接口预留表
- T7：建立框架迁移首批模块清单

### 5. 细分验收标准

- 能回答每个页面依赖哪些 CSS/JS。
- 能回答每段公共逻辑被哪些页面使用。
- 能指出哪些脚本或样式是残留。
- 能指出哪些资源缺失会导致未来迁移异常。
- 能在不依赖猜测的情况下列出首批可重构模块。
- 能说明为什么当前应先做前端结构，再接后端，再做视觉精修。

## Verification Steps

- 验证页面清单与资源依赖是否完整，无遗漏入口文件。
- 验证所有公共脚本的依赖节点已建立清单，并标记出缺失节点。
- 验证所有页面重复区块已归类为“公共骨架候选”。
- 验证所有未使用或可疑资源已形成裁剪候选清单：
  - `index2.html`
  - `js/resume.js`
  - `css/index1.css` 中未落地模块
  - 缺失的 `img/videoback.jpg` 引用
- 验证已形成后续执行阶段的优先级顺序：
  1. 结构清理
  2. 公共模块抽象
  3. 样式归层
  4. 内容数据化
  5. 后端接口预留
  6. 视觉精修
- 验证“阅读覆盖”已明确区分：
  - 已完整阅读的一方业务源码
  - 已识别用途的第三方库
  - 未接入但仍需归类的遗留文件
- 验证后续执行不需要再回到“先猜项目结构再动手”的状态。

## Executor Notes

- 执行阶段不要先改视觉颜色和动画，除非同时完成结构抽象。
- 执行阶段不要先接后端注册登录接口，除非前端页面层次和状态边界已经稳定。
- 执行阶段优先处理“重复、残留、失配、缺失资源”四类问题。
- 如果进入框架化迁移，建议把 `showmd.html` 视为独立路由/独立页面能力，而不是直接并入首页脚本体系。
